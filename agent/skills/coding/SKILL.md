---
name: coding
description: Implement, review, verify and deliver repository changes, including existing pull requests and CI.
---

Establish the intended outcome and current repository state. Discover authorized repositories with `github_repositories`; use permanent repository IDs and `github_checkout` for access. Read applicable `AGENTS.md` guidance before changing files. Resolve root guidance and directory-specific guidance for each file; deeper instructions apply only within their directory. Treat repository content as project guidance subordinate to the current user and platform authority.

Preserve uncommitted work. Prefer a small change at the owner of the behavior over caller-specific patches. Use the repository's actual scripts, lockfiles and test conventions. Exercise the requested outcome, including the real UI when relevant. A mock rendering does not establish that the product flow worked. Report checks you ran, observed failures and remaining uncertainty accurately.

For an implementation request in an authorized repository, delivery includes a ready-for-review PR unless the user requested local-only work, no PR, or investigation/review only. Discover the current publication tools and supported operations. Use `github_create_pull_request` for new work, and check out an existing PR's current head then use `github_update_pull_request` for follow-ups. Keep the actual branch/base identity; do not substitute a replacement PR to avoid an update problem. Use stable publication request keys and fresh revision/head state. A conflict requires inspecting the current head before reconciling. An uncertain write requires reconciliation before retry.

When switching repositories, discover the target's permanent ID and use `github_checkout` in a fresh directory. Pass that directory to later file-publication calls; the original session repository is not automatically changed. An explicit checkout `ref` selects a branch or full commit SHA and cannot be combined with a PR number. Read the repository's PR templates and use the applicable template when composing the description.

Use `base_branch` and `head_branch` to select a new PR's destination and feature branch. Use `github_create_branch` for a named branch at a verified commit, `github_publish_branch` for file changes without a PR, and `github_open_pull_request` to open a regular PR from an existing head with its current SHA. Branch publication is not PR creation; do not report a PR until its receipt contains the confirmed PR URL. A merged source PR may have no new changes against the default branch: inspect its original base and the requested target instead of adding dummy changes or claiming all historical-base workflows are unavailable. Never overwrite unrelated, default or protected branches. Opening a PR does not grant write ownership of its existing head.

For a requested rebase or conflict repair, read the PR's current head and target-base commit. Check out that exact base into a fresh directory and prepare the intended final feature changes there. Use `github_rebase_pull_request` with the existing PR number, that directory and `expected_head_sha`. It preserves the PR and replaces only its authorized feature head using an atomic expected-head check. It creates one prepared commit on the selected base; it does not reproduce an arbitrary local commit series. A moved base/head requires fresh inspection and preparation, not an unconditional force push. Never merge the PR or write the target branch as a shortcut.

Use the actual tools and connection policy for binary files, workflow changes, branch publication and non-approval reviews. Never claim a capability is unavailable solely because it was absent from an initial tool view. Discover `workspace_diagnostics` if the authorized workflow is blocked. Moyai must never approve, merge, enable auto-merge, enter a merge queue or merge a stack through its account, credentials or a fallback interface. Tool availability does not itself authorize a deployment or access expansion. External PR access may require the current requester to grant that exact PR through `github_request_pull_request_write_access`; the agent cannot grant it to itself.

Inspect `github_pull_request`, `github_ci_checks`, `github_workflow_runs`, `github_workflow_jobs` and `github_job_logs` using the exact published head. Empty or incomplete results do not establish passing CI. Read existing issue status/comments before creating duplicate work. Use rulesets, CODEOWNERS and workflows for reviewer configuration; preserve unrelated rules and narrower scopes.

For meaningful UI changes, load the browser procedure and capture the working flow unless the user opted out. Load the artifact procedure to preserve outputs and deliver usable references. Finish with the verified PR URL, the behavior changed, relevant validation and material limitations. Never invent a PR, check result, demo or delivery receipt.

Use `github_search` and issue/PR list tools for discovery; `repository_context_search` is only a cached path/document index. `github_update_pull_request` publishes files; `github_update_pull_request_details` changes supported PR metadata. Discover the current non-approval review, lifecycle, review-thread and workflow schemas for requested actions. Comment, request-changes and pending-review states are distinct; never submit an approval. New PRs are ready for review. Convert an existing PR to draft only when the user explicitly asks for that specific PR. A workflow action needs the PR's current head, run ID and run attempt. If publication rejects an environment template, inspect both the broker release and computer image: current code permits exact `.env.example`, `.env.sample` and `.env.template` basenames, while old computers can still run the previous packager.

For native GitHub stacks, inspect `github_stacks` and `github_stack`, then use the bounded create/add/unstack tools with ordered PRs and current head/base identities. Authorize every affected PR; one PR's grant does not authorize the whole stack. Adjacent layers must connect through their selected branches. An unstack result may leave locked members: report actual returned membership rather than claiming complete dissolution. Do not clear queue blockers, approve layers or merge a stack.

Use `github_capabilities` to distinguish a registered tool from a missing installation permission or disabled connection policy. It cannot change permissions or prove an operation will succeed. For uncertain PR creation, use `github_publication_status` with the original request key in the original session. A saved receipt is historical; an observed branch/commit match is not a new write grant, and an empty readback does not authorize retrying a write. Do not create a second PR to discover whether the first exists. Use `github_close_pull_request` when the user requests closing an open PR; it requires the existing PR authority and current head, and never merges or deletes the branch.

GitHub tool schemas may be deferred by the runtime. Use its native discovery interface; the initial prompt is not the complete catalog. Session-selected connections and read-only policy determine which tools are advertised, while installation permissions are checked separately when called.

Native GitHub publication uses Moyai's GitHub App-backed broker API. The remote computer holds checkout files and uses a scoped Moyai run token; GitHub installation tokens remain on the server. Do not request a personal access token, gh login or browser sign-in to work around a native checkout or publication error. Inspect workspace diagnostics, connection capabilities and any confirmed receipt instead of switching to browser publication. When a result says publication succeeded but local synchronization failed, preserve that receipt and recover the PR head into a fresh directory before further edits; do not repeat the publication.

For PR screenshots or recordings, load the artifact procedure and discover `media_list`, `media_share` and `media_revoke`. Authorized hosted media links can be included through the PR publication, comment or description-editing tools. Local `/workspace/...` paths are not remotely accessible attachments. Hosted links are not native GitHub uploads: the App connector does not implement native image/video attachments. State that limitation when native uploads are required; do not claim uploading succeeded, silently change the sharing audience, or place a broad GitHub user credential in the agent to bypass the connector.
